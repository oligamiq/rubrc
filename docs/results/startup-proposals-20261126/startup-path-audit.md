## Executive finding

**The strongest bounded candidate is to use the full inline project configuration from initialization on the existing sysroot-first startup branch, eliminating its later configuration transition.** Current “lightweight” initialization does not necessarily mean no project loading: `linkedProjects: []` permits filesystem discovery, and the normal filesystem already contains the same project as a manifest. The activation transition then replaces the manifest-backed project with an inline project, whose identity differs even when its crates/sysroot payload matches.

This is a demonstrated duplicate *workspace-load path under normal successful discovery*, not a measured count of two completed crate-graph builds or repeated 14-second semantic computations. Instrument that distinction before assigning savings. The forced document reopen and redundant writes are separate candidates; keep them unchanged in the first experiment to isolate the configuration effect.

### D. Duplicate main-document writes are demonstrable but likely a smaller target

For an unchanged normally opened document, source calls for pre-start VFS write, initial didOpen mirror, activation snapshot write and reopen didOpen mirror. [Document middleware:57–78](</home/oligami/projects/rubrc/page/src/rust_document_sync.ts#L57-L78>) and [queueWrite:273–294](</home/oligami/projects/rubrc/page/src/rust_document_sync.ts#L273-L294>) do not deduplicate; [workspace writer:14–23](</home/oligami/projects/rubrc/page/src/workspace_sync.ts#L14-L23>) encodes, copies and sends JSON each time.

But repeated transport writes are not necessarily RA invalidations (see VFS equality above). More importantly, activation captures text **before** the graph wait and writes it **after** the wait; edits can make it stale temporarily. The strict reopen mirror restores the latest contents. The [edit-during-activation test:694–781](</home/oligami/projects/rubrc/page/src/rust_lsp_client_test.ts#L694-L781>) deliberately requires initial+latest writes and latest-write completion before didOpen. Never simply delete the last mirror. A later generation-scoped serialized writer could skip only previously **successfully acknowledged identical content**, invalidate on failure/reset/external mutation, and preserve strict failure propagation and latest-edit flush. This saves bytes/calls, not proven seconds.

### E. Probe duplication and waiting are possible costs, not graph rebuilding

Graph readiness polls every 5 s with a 10 s per-request deadline ([readiness constants:50–53](</home/oligami/projects/rubrc/page/src/rust_analyzer_readiness.ts#L50-L53>)); attempt 2 in all four candidate rows means a fixed inter-attempt wait occurred. The endpoint merely views an analysis snapshot ([handler:330–336](</home/oligami/projects/rust-analyzer/crates/rust-analyzer/src/handlers/request.rs#L330-L336>)); a second poll is not a second rebuild. Missing timestamps for graph application versus poll response prevent estimating avoidable detection latency. Do not claim 5 s is entirely removable: the graph could become ready near the second poll.

The semantic gate opens just before the explicit readiness inlayHint probe ([client:221–224](</home/oligami/projects/rubrc/page/src/rust_lsp_client.ts#L221-L224>)). Editor-triggered inlay/code-action requests can compete with that probe; no trace proves duplication today. Keep the explicit probe unless a shared result is tied to the same graph generation, URI, document version and requested range. Readiness requires exact latest diagnostics, a quiet window and stable version around the hint response: [readiness:308–369](</home/oligami/projects/rubrc/page/src/rust_analyzer_readiness.ts#L308-L369>).

It is consumed with `take()`, not re-deserialized every configuration change.

Do not remove this validation as allegedly redundant priming. `cachePriming.enable:false` is not “cache disabled.”
- `loaded` and `merged` prove adoption, not a hit on every later query. Optional audit counts WillExecute defmaps/item trees, probes std crates and compares input signatures ([cache audit:86–169](</home/oligami/projects/rust-analyzer/crates/rust-analyzer/src/semantic_cache.rs#L86-L169>)); it finishes at the first graph containing a non-stdlib crate ([reload:881–891](</home/oligami/projects/rust-analyzer/crates/rust-analyzer/src/reload.rs#L881-L891>)). **If initial discovered project merges cache, this audit may finish before activation's second graph and reopen.** Existing audit therefore cannot establish preservation throughout the full startup path. ## First bounded experiment (proposal only)

### Preparation: low-overhead causal trace

Use the existing batching-on artifact/configuration as baseline. Trace counters and sparse phase timestamps, not per-query textual spam in the timing arm. Obtain an instrumented diagnostic run separately from acceptance timing.

Minimum events: initial/full configuration fingerprint and source (init/response); discovered manifest list; fetch enqueue/coalesced/start/end cause+generation; workspace equality result; graph begin/applied/complete identity and crate count; cache load/merge/reject plus Salsa revision/source-root moves; document open/close/change (URI, version, byte length/hash); mirror start/ack/failure (sequence/hash); diagnostic schedule/cancel/complete/publication (server version, generation, syntax versus semantic, result hash); explicit and editor hint request/response IDs/ranges; graph poll start/response and graph application timestamp. Keep monotonic clock domains aligned.

Specifically measure std query **executions versus validations/reuses** across first load, activation, reopen and semantic readiness. Existing browser readiness test state copies the final version into diagnostics/inlay fields after success ([test API:402–412](</home/oligami/projects/rubrc/page/src/lsp_test_api.ts#L402-L412>)); it is not a request history. Add raw protocol evidence rather than treating these summary fields as causal telemetry.

### Candidate 1: full inline initialization only when sysroots are installed

On the existing sysroot-first branch, pass an explicit startup mode/capability into analyzer initialization. Initialize with the full inline project settings and use the **same settings** for workspace/configuration from the beginning. Skip only the activation didChangeConfiguration/state transition. Continue to wait for the complete main/core/alloc/std graph, perform existing document synchronization/reopen, require fresh versioned diagnostics and explicit semantic probe, then publish ready. Keep the cache-unavailable analyzer-first branch unchanged. Do not change the cache validator, build settings, lock batching, document lifecycle, diagnostics or independent-memory layout in this experiment.

Why first: the source identifies a concrete initial-manifest → inline reload route; the cache-first order already guarantees sysroot presence; this avoids silently attempting full initialization before prerequisites. Cache rejection after install still has sysroots available, so correctness must hold by cold analysis. “Cache enabled” should be named as a sequencing prerequisite, not trusted as a hit flag.

Expected evidence (not a promised speedup): one intended workspace load/configuration identity in the candidate, fewer metadata/graph transitions if the baseline trace confirms them, unchanged semantic answers and no late stale update overriding full config. Compare end-to-end totals, not just activation: initialization may absorb work previously attributed to activation.

### Follow-ups, separately controlled

1. Keep Rust document open throughout activation only after adding graph-generation-aware readiness that can accept a genuine post-load diagnostic without waiting forever for an event that already arrived. Simply removing the reopen while retaining the unconditional diagnostic reset can hang. Alternatively delay *first LSP document synchronization* until the full graph, while keeping editor syntax/editability; do not change Monaco to plaintext for the entire startup just to suppress traffic.
2. Deduplicate acknowledged identical VFS writes in one shared serialized path, preserving failure retries, latest edits and reset isolation.
3. Reduce graph-ready detection latency with a graph-completion/status wakeup followed by the same full graph proof and bounded fallback polling, not blind removal of the readiness check.
4. Only after request traces show contention, share/defer duplicate editor inlay requests without removing the explicit semantic proof.
