# Rust-Analyzer WASI Metadata Boundary Trace Design

## Goal

Identify the first internal rust-analyzer WASI boundary that the stalled browser path fails to cross after all four `host_run_cargo` calls return status 0.

The first run is observation-only. After that run identifies a narrow candidate boundary, the investigation may apply one experimental fix at a time before the root cause is fully proven.

## Current Evidence

- The passing Deno path completes diagnostics in about 73 seconds.
- The browser path remains at `querying project metadata` for a verified 300-second observation window.
- Browser host Cargo calls with correlation IDs `1`, `3`, `5`, and `7` all return status 0.
- The browser snapshot has no active tracked Cargo, rustc, stdout, or stderr operation and has an empty public VTP queue.
- During the browser stall, WebShell can start later `rustc_opt` tasks on the same VTP. This falsifies a global VTP starvation or globally stuck Cargo/child bridge hypothesis.
- `ProjectWorkspace::load` spawns a scoped Cargo metadata thread. Inside that child thread, `FetchMetadata::exec` invokes `host_run_cargo` synchronously, reconstructs returned buffers, validates UTF-8, extracts a JSON line, and parses metadata. The parent workspace-loading thread later joins that child.

## Scope

Instrumentation is added only in the isolated rust-analyzer worktree `/tmp/opencode/rust-analyzer-metadata-trace`, based on commit `b1829d7770` from `feat/wasi-support`.

The rust-analyzer request JSON gains an optional observation-only `trace_id`. Rubrc's existing `host_run_cargo` trace may read that field and record it beside the host outer ID without changing command execution or response data. `wasi_virt_layer` source logic remains unchanged.

An isolated rubrc snapshot may replace `crates/vfs/lsp_opt.wasm`, add the `trace_id` observation, rebuild generated VFS assets, and extend test-only observation timeouts.

No instrumentation is added to Cargo, rustc, browser shim packages, generated bindings, or upstream registry caches.

## Trace Format

Rust-analyzer does not write boundary traces to stdout or stderr. It imports a numeric `host_trace_boundary(trace_id, stage, value_1, value_2)` function from the existing `__wasip1_vfs-host` module. During `wasi_virt_layer build`, that import resolves directly to a VFS Rust export in the combined Wasm component; it does not re-enter Rust through a JavaScript callback. Rubrc implements the export with a nonblocking `try_lock` write into the existing 64 KiB VFS debug ring. Lock contention drops the event, increments a dropped-boundary counter, and returns immediately.

The VFS formats retained events with the prefix `[ra-wasi-boundary]`. Every Cargo invocation receives a rust-analyzer-local monotonic ID generated by `AtomicUsize::fetch_add` with relaxed ordering. This uses the existing `wasm32-wasip1-threads` shared-memory execution model rather than introducing a new synchronization mechanism. That ID is included as optional `trace_id` in the existing Cargo request JSON. The VFS host trace records both its outer ID and the RA ID, providing exact cross-boundary correlation even when calls overlap.

Lines contain only:

- invocation ID;
- static stage name;
- return code or success boolean;
- stdout/stderr/request byte lengths where relevant.

Command arguments, environment values, Cargo JSON, source text, stdout contents, and stderr contents are never logged. Stage names are a fixed numeric enum shared by the rust-analyzer instrumentation and the VFS formatter.

Instrumentation is compiled only for `target_os = "wasi"`. Non-WASI source and behavior remain unchanged. The VFS ring mutex makes each retained line atomic; no JS or WebWorker message is sent on the observed rust-analyzer thread.

## Boundaries

### FFI Layer

In `crates/toolchain/src/wasi_cargo.rs`, record:

1. `ffi:enter` immediately before `host_run_cargo`.
2. `ffi:return` immediately after the imported function returns.
3. `buffers:borrowed` after validating returned pointer/length pairs.
4. `buffers:copy-enter` before stdout and stderr are copied into owned `Vec<u8>` values.
5. `buffers:copied` after both copies complete.
6. `buffers:free-enter` immediately before releasing host allocations.
7. `buffers:freed` immediately after host allocations are released.
8. `invoke:return` immediately before returning `WasiCargoOutput`.

### Metadata Layer

In `crates/project-model/src/cargo_workspace.rs`, record:

1. `metadata:invoke-enter` and `metadata:invoke-return` around `invoke_cargo`.
2. `metadata:utf8-enter` and `metadata:utf8-return` around UTF-8 conversion and JSON-line selection.
3. `metadata:parse-enter` and `metadata:parse-return` around `MetadataCommand::parse`.
4. `metadata:finished` immediately before the existing `cargo metadata: finished` progress callback.

### Workspace Layer

In `crates/project-model/src/workspace.rs`, record:

1. `workspace:cargo-spawn-enter` immediately before spawning the Cargo metadata scoped thread.
2. `workspace:cargo-spawn-return` immediately after `scope.spawn` returns its handle.
3. `workspace:cargo-join-enter` immediately before joining the Cargo metadata scoped thread.
4. `workspace:cargo-join-return` immediately after a successful join.
5. `workspace:cargo-join-error` before propagating a panic or failed scoped-thread result.
6. `workspace:cargo-map-return` after converting parsed metadata into `CargoWorkspace`.
7. `workspace:load-return` immediately before returning the loaded `ProjectWorkspace`.

Each multi-step WASI trace scope uses an unwind guard that emits a static `scope:unwind` line if normal return is not reached. The build retains the existing `panic=unwind` setting. A non-unwinding trap may still stop before the guard runs; in that case the final `*-enter` stage remains the evidence boundary.

## Comparison Method

Build rust-analyzer once for `wasm32-wasip1-threads` with the existing panic-unwind flags, optimize the same way as the current `lsp_opt.wasm`, and record its SHA-256.

Use that exact Wasm binary for one passing Deno diagnostics run and one browser run with a 300,000 ms page timeout, 360,000 ms Puppeteer protocol timeout, and an outer timeout that exceeds build plus observation time. Do not rebuild between runs.

For each path, collect all `[ra-wasi-boundary]` lines and compare by local invocation ID and static stage. The conclusion records:

1. the last stage reached by both paths;
2. the first stage reached by Deno but absent in browser;
3. whether browser stopped before FFI return, buffer ownership transfer, UTF-8 extraction, metadata parse, workspace join, or workspace return.

Concurrent output order is not used to infer pairing. The VFS snapshot includes the dropped-boundary count; a dropped event overlapping the first apparent divergence makes that run inconclusive.

The nonblocking imported trace call still adds a small cross-Wasm call and can affect scheduling. The experiment validates that the instrumented Deno path still passes and the instrumented browser path still reproduces the same progress stall. If the instrumented browser unexpectedly passes, crashes earlier, drops boundary events, or changes the host call count, no internal conclusion is drawn; rerun an uninstrumented control before changing the trace mechanism.

## Error Handling

Trace emission is best effort and nonblocking. A trace write failure must not replace the underlying Cargo or metadata result. Existing errors continue through their current paths.

If the browser reaches every planned boundary, this experiment reports that the waiter lies after `ProjectWorkspace::load` and defines a new observation boundary; it does not guess a fix.

If the instrumented build changes the failure or prevents startup, the run is invalid and the instrumentation/build difference is investigated before drawing conclusions.

## Experimental Fixes

An experimental fix is permitted when the boundary trace or direct code path supports one explicit hypothesis. Each experiment:

- changes one behavior only;
- starts from a recorded failing browser control;
- adds the narrowest available regression or contract test before the change;
- uses the same diagnostics acceptance criteria as the control;
- records whether Deno behavior remains passing;
- is not described as the root cause merely because timing changes.

If a fix makes the browser pass, remove that fix while retaining the observation harness and reproduce the failure once. Reapply the fix and verify the pass once more. The baseline must therefore fail twice and the fix must pass twice in an interleaved fail-pass-fail-pass sequence. If either state is nondeterministic, use at least three isolated runs per state and report the observed rate instead of claiming a root cause.

Failed experimental fixes are reverted in the isolated snapshot before testing another hypothesis. Multiple candidate fixes are never stacked in one run.

## Verification

- Source tests assert that every stage is WASI-gated, contains no payload formatting, and brackets the intended expression.
- Existing rust-analyzer tests covering `wasi_cargo` request/result reconstruction and Cargo metadata parsing continue to pass where runnable.
- The instrumented lsp Wasm reaches the existing Deno diagnostics success path before it is used for browser comparison.
- The Deno and browser runs use an identical recorded Wasm hash.
- The final report includes exact commands, durations, hashes, complete boundary stage sets, and any residual unobserved interval.
- Any successful experimental fix includes fail-pass-fail-pass evidence and focused regression results before it is proposed for production integration.
